# 行内主行的光标竖条：y 没有基准尺子（未收口 · 2026-11-01 晚）

> **状态**：**未修**。本文是调查记录 + 下一步方案，不是规格。
> 现行规格见 [`../design/位点与结构导航.md`](../design/位点与结构导航.md) §6.2；
> 待办见 [`../后优化清单.md`](../后优化清单.md) **F11**。
> 全部数字都是探针实测（`flutter test`，dpr 1，正文 16pt）。

---

## 一、现象（用户 2026-11-01 两张截图）

同一行、同一个位点（`f^{\prime}_{+} | f^{\prime}_{+}` 之间），**后面加字就跳**：

| 文档 | 竖条中心 | 与"无后续"差 |
|---|---|---|
| `$f^{\prime}_{+}f^{\prime}_{+}$` | 113.0 | — |
| `$f^{\prime}_{+}f^{\prime}_{+}x$` | 108.8 | **4.2 px** |
| `$f^{\prime}_{+}f^{\prime}_{+}\xi\omega$` | 108.8 | **4.2 px** |

而**文字侧**竖条（同一行、`甲` 之后）中心恒为 **109.0**。
⇒ "无后续"那一档既跳，又比文字侧低 **4.0 px**。

（U3 那条守卫 `caret_main_row_height_test` ① 一直是绿的：它的文档 `甲乙 $a+b$ 尾` **带尾随文字**，
恰好落在"有后续"那一档。）

## 二、口径（用户 2026-11-01 确认）

- **竖条的行由"这一行"决定**，不由"最近的字形"决定 —— 三条：
  - **x**：位点表给的偏移（稳）；
  - **h**：行内主行 = `字号 × 1.25`（U3 已定，**不动**）；子层/行间仍按当地行盒自适应；
  - **y**：**缺**。现在借的是"挑中的那个字形盒中心"，所以随内容/邻居变。
- 行内 vs 行间**光标高矮本来就不同**（16pt vs 20pt 字号），**不许强行统一**（用户明确否掉）。

## 三、试过的四条路（全部回滚，一行没留）

| # | 做法 | 结果 |
|---|---|---|
| ① | 主行只在"最高的那类字形"里挑盒 | 邻居稳定到 0.6px，但 `$a+b$` 与文字侧差 **0.89** ⇒ U3 红 |
| ② | 中心改用"锚点**行盒**中心" | 行盒 0.0..16.2 三档一致 ✓，但 `$a+b$` 差 **0.89** ⇒ 仍红（行盒随行长变） |
| ③ | 问段落 `getOffsetForCaret(pos, Rect.zero)` | 差 **2.3** ⇒ 仍红 |
| ④ | 同上但 prototype 给真高 `Rect.fromLTWH(0,0,0,h)` | 数字与 ③ **完全相同**（引擎这里不吃 prototype 高度） |

另：`getDistanceToBaseline` **不能在 build/帧末调用**（只在 layout/paint 阶段），
`RenderParagraph.computeLineMetrics()` 在本版 Flutter **不存在**；`Math` / `RenderLine` 都不报 alphabetic 基线。

## 四、真正的尺子在哪（本次最重要的发现）

DocView 画**文字侧**竖条用的是它自己的"一把尺子"：

```
_caretInset = (行盒 − 字号×1.25) / 2      // doc_view.dart
竖条 y      = 行顶 + _caretInset          // 高 = 字号×1.25
⇒ 竖条中心 = 行顶 + 行盒/2                // 即：**居中于行盒**
```

而段落 API 的 `getOffsetForCaret` 给出的是**引擎排版器**的零高光标顶（比这把尺子低 2.3px）。
**两者不是同一把尺子** —— 这就是 ③④ 差 2.3 的原因，也是为什么"问段落"永远差一点点。

⇒ **行内公式必须拿到的是 DocView 的"行顶 + 行盒"**，不是段落 API 的数。

## 五、下一步（方案已定，只差实现）

把"这一行的几何"从 DocView 传到竖条（一行参数链，不新增机制）：

```
doc_view（已知：单元 y、_lineBox、行内公式的占位盒）
  → inline_math_text（新增参数：本行"行顶到公式盒顶"的偏移 + 行盒高）
  → math_caret（行内主行：y = 行顶 + 行盒/2 − 公式顶；h 不变）
```

**必须在同一帧内拿到**（不能靠第二帧补），否则会闪一下。
首选在 DocView 构建该单元时就已知的数（`s.y` 与 `_lineBox`），避免再问渲染树。

### 验收（守卫已写好，改前必红）

1. **同一位点 × 邻居组合**：无后续 / `+x` / `+ξω` / **前面有正文** ⇒ top 与 h **逐个相等**（容差 0.6）；
   —— 2026-11-01 实测改前差 **4.2px**，可作"改前红"证据；
2. **与文字侧竖条同中心**：`|公式侧 − 文字侧| < 1.0`；
3. 既有 `caret_main_row_height_test`（U3，容差 0.5）**不许放宽**；
4. 行内 vs 行间的高矮差**保持**（那是设计内差异，不要"顺手统一"）。

## 六、别踩的坑

- **不要**改 `h`：U3 定的 1.25em 是对的；问题只在 y。
- **不要**用"字形盒中心"或"行盒中心"凑：前者随邻居变，后者随行长变（都实测过）。
- **不要**在 build 里问 `getDistanceToBaseline`（断言）。
- 行间块（`mathStyle == display`）走的是另一支（`caretBarRect` + 行盒 × 0.84），本批不碰。
