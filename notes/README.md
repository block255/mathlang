## 一、状态与权威顺序

| 标记 | 含义 | 能否作为实现依据 |
|---|---|---|
| **现行规格** | 与当前代码/发布一致，改行为必须同步 | ✅ |
| **现行参考** | 解释结构/理由，不直接规定行为 | 参考 |
| **现行清单** | 待办/路线图，状态可能滞后于代码 | 以条目证据为准 |
| **历史** | 记录当时的事实/决策，**只读** | ❌（查证据可以） |
| **草稿** | 未诊断/未拍板/原始收件箱 | ❌ |
| **发布** | 对外 Release 正文 | 对外口径 |

**权威顺序（冲突时）：**

```text
代码 + 测试  >  Release 说明  >  design 现行规格  >  台账/路线图  >  交接快照/开发日志  >  草稿
```

`最后核对` 列的两种写法：

- **2026-10-25 校对**：本次逐条核对并修正过。
- **2026-10-25 索引**：只登记了位置/状态，没有逐条复核内容。

## 二、先看哪几份（最短路径）

- **新会话/接手**：`README.md` → 本页 → [`后优化清单.md`](后优化清单.md) §一（影响每天都用）→ [`handover/会话状态快照-20261102.md`](handover/会话状态快照-20261102.md)（**最新交接**）→ **下一批（选择边界与剪贴板）看 [`handover/20261102-选择边界与剪贴板.md`](handover/20261102-选择边界与剪贴板.md)** → **先读 [`design/只读基准.txt`](design/只读基准.txt)（最高优先）** → 对应 design 规格（行/段/空行看 [`design/行与段-空行基准.md`](design/行与段-空行基准.md)）。

- **发布**：`CONTRIBUTING.md` §8 + [`release/v1.1.0.md`](release/v1.1.0.md) + `signing/README.md`。

## 五、维护规则

1. **新文档先登记**：在本页加一行，写清状态、最后核对日期、用途；与内容同一提交。
2. **改行为就改权威**：规格/台账/Release 至少更新一处；不要只在会话快照里写“已修”。历史文档可以保留原标题，但本页必须标成“历史”。
3. **过期加横幅**：在标题下写“本文是历史快照，现行看 X”，不要删除；删除会丢失决策证据。
4. **不复制整段**：同一批次/根因只在权威处写全，其它文档放链接。
5. **会话快照只追加**：它记录“当时发生了什么”，不承担“现在是什么”的职责。
6. **Release 正文逐字一致**：`notes/release/vX.Y.Z.md` 与 GitHub Release 必须相同；改一处同步另一处。
7. **计数只写一处**：测试条数/版本号/体积写在 Release 或 README；规格里不重复。
8. **链接要能点**：新增/改名文档后，检查本页与根 README 的相对链接。
