## 二、★ 为什么 bug 与手感是同一张网

> **bug = 某张地基表漏了一格，或多出了一份判据。**
> **手感功能 = 某张地基表的一个新消费者。**

所以"待修 bug 清单"和"待做手感清单"**不是两条平行线**，它们会撞在同一段代码上：

| 已知 bug | 与哪个手感功能**共用**同一段代码 |
|---|---|
| 粘贴 `$\frac{}{}$` 后"消失"（光标归属有洞） | **失焦不画光标** · **光标闪烁**（都是"光标画在哪"） |
| `Enter` 把公式劈开 | **剪贴板粘贴**（粘一大段进来同样不能劈开公式 —— 守门人已是同一入口 ✓） |
| 退格删掉收尾 `$`、编码爆出来 | **拖选后删除**（同一个"删除对象"模型） |
| **删不掉根号** | ★ **归 ②③④，不归删除规则**：结构层位点（`\sqrt{}` 的 tex 末尾）**今天就能删**；缺的是**那一层可达 / 可点** ⇒ **双击选词 / 三击选段 / 虚线框自绘 / 范围可见**（都在问"结构边界在哪、这一层点得到吗"） |
| ★ **点分式整体后面删只删了分母的 `b`** | **拖选后删除 · 双击选一个分式**（同一张"对象"表：**对象 = 与光标同层的紧邻渲染对象**） |
| **点根号末尾一律判"根号内"** | **拖选跨过结构** · **双击选一个分式** · **虚线框自绘** · **公式范围可见**（全要"结构几何"） |
| **行间公式外侧的光标消失** | 失焦不画光标 · 闪烁（同上） |
| 点不到空行 | 拖选到空行 · 空行上的光标（"空行是一等公民"） |
| W1 点不到末尾分式外面 | **鼠标拖选**（同一张归属表） |

**真正独立、不交错的只有两件**：**撤销分组**（`Edit` 栈粒度）· **拖到边缘自动滚动**（纯视口）。

## 三、"多份判据必然有一份是错的"—— 实例归因

设计稿 §11.15 已记过一条"被验证了四遍"的经验（注入 ↔ 坐标）。2026-10-15 又发生了一整轮：

| # | 现象 | 归因类型 |
|---|---|---|
| 1 | 粘贴 `$\frac{}{}$` 消失（连光标一起） | **四份判据**（`_caretInSegment` / `mathPlaceholderAt` / `caretParagraphOffset` / `_computeCaretRect`），只有一份不知道边界要放宽一格 |
| 2 | `Enter` 把公式劈开 | **插入侧从来没有守门人**（§四"永不留下半个坏公式"只做在删除侧） |
| 3 | 退格只删掉收尾 `$`、编码爆出来 | **规格缺口**：§3.3 的删除规则只有"公式首"一行，"公式尾"从来没写 |
| 4 | `Delete` 在 `\frac{a}{b}` 开头把 `\` 删掉 | **判据不完整**：`_atomRightOf` 要求"中间只许夹 `{` `}` 和空格" |
| 5 | 公式 A 末尾 `Delete` 删掉了公式 B 的 `$` | **边界自己写了一套**（没回到"可见对象"通则） |
| 6 | 删不掉根号 | **判据不可达**：§4.3 只在 `u.end` 那一个位点生效，而空槽里唯一的位点是 `u.end - 1` |
| 7 | 点根号末尾一律判"根号内" | **用错了判据**：命中用的是"最近**字形叶盒**"，而 `√`/横杠/分数线**不是字形**，在命中系统里根本没有盒 |
| 8 | ★ 点分式**整体**后面删，只删掉分母的 `b` | **判据不带层级**：`_atomLeftOf` 只找"最近的可见原子"，**跨过了结构的边界**（§4.0 通则的由来） |

⇒ **8 条里 7 条是"多份判据"或"判据不完整 / 不可达 / 不带层级"。**
**可推广的检查**：凡"两个序列/两个坐标系必须对应"的地方，测试要**全域**断言（完备 / 唯一 / 往返），
不能逐例抽查 —— 逐例测试永远漏得掉"某个偏移没人管"。

## 五、结构几何（②）的规格草案 —— 只定轮廓，**实现前先探针**

**为什么单独定**：它是新地基，且**五个消费者**都等它；同时它踩在我们已知的几个引擎坑上
（细线被 `kMinLeafWidth` 过滤、数学字形画出根盒之外、`Rect.contains` 下边界开区间）。

### 5.1 输入输出

```
输入：tex（源空间） + 该 Math 的叶盒列表（局部坐标，已有：leaf_boxes.dart）
输出：结构表 List<StructureBox>
        { kind: 分式 / 根号 / 大算符 / 环境 / 空槽 / 整段公式
          span: 源码区间（绝对或相对 tex）
          rect: 屏幕矩形（局部坐标） }
```

**做法（草案）**：叶盒 ↔ 可见原子的对应关系**已经有了**（`leaf_boxes` + `visible_atoms`），
而**结构在源码里的跨度**也**已经有了**（`caret_sites` 的槽区间 + `structureUnits`）。
把两者合起来就能算：**结构整体盒 = 它各槽内原子盒的并集 ∪ 装饰盒**。

### 5.2 三条全域不变量（学"光标归属表"那套）

| | 性质 |
|---|---|
| **P1 完备** | 每个结构实例都有矩形（不许漏） |
| **P2 包含** | 子结构的矩形 ⊆ 父结构的矩形 |
| **P3 顺序** | 同级结构的矩形在主轴方向上**不重叠**，且顺序与源码顺序一致 |

### 5.3 已知风险（探针要先量这些）

- ~~**装饰盒**：分数线 / 根号横 / 括号 / 上下限连线 —— 它们是不是叶盒？会不会被 `kMinLeafWidth`
  或宽度上限过滤掉？~~ ★★ **2026-10-15 晚已量清**（数据见《位点与结构导航》§11.17 补充）：
  **结构盒 = `RenderCustomLayout<...>` 节点**（`_SqrtPos` / `_FracPos`），**真实可用**；
  失真的是**内层**那张装饰矢量图（1833×1080，被 `RenderFittedBox` 缩放到真实尺寸）。
  ⇒ ② 的输入 = **全部 RenderBox**（不只叶盒），结构实例按**前序**与节点对齐。
- `\left( \right)` 的括号盒、`\sum` 的上下限盒、环境的行盒，各是什么样（**待量**）
- 数学字形**画出根盒之外**这一条（S3 踩过）会不会让"并集"偏大

★ **纪律**：**先写探针把上面这些量出来，再定实现**（同 `\\` 那次 —— 先验通路，再写码）。

★★ **2026-10-16：三批探针跑完，表已落地**（数据与结论全部写进《位点与结构导航》**§11.24**）：

- ✅ **结构盒 = `RenderCustomLayout<_FracPos>` / `_SqrtPos` / `_ScriptPos` / `RenderRelativeWidthColumn`
  / `RenderEqnArray` / `RenderCustomLayout<int>`**；**装饰内层矢量图在 `RenderFittedBox` 里**
  （2133×1080，被它缩到真实尺寸 ⇒ 几何取外壳）。
- ⚠️ **推翻**："按节点类型配对"**不成立**（同一个结构在不同 `MathStyle` 下落**不同节点**）；
  "源码里 `^`/`_` 个数 = `_ScriptPos` 个数"**不成立**（算子的上下限折进了算子那个节点）。
- ⇒ 最终对齐规则：**源码侧结构对象（前序）↔ 渲染侧结构承载节点（前序），按位置 zip**
  （只对有节点的对象 zip），并断言"数量相等 + 类型相容"。
- ⇒ 矩形 = **节点盒 ∪ 叶盒并集 ∪ 子结构矩形**（最后一步自底向上，是 **P2 包含性的唯一保证**）。
- ⚠️ **`\left( \right)` 的括号盒** = `_RenderLayoutBuilderPreserveBaseline`（**装饰/定界符，不是结构**）；
  `\sum` 上下限 = `RelativeWidthColumn`（display）/ `_ScriptPos`（text）；
  **环境行盒** = `RenderEqnArray` 的子 `RenderLine`（`pmatrix` / `substack` 是 `CustomLayout<int>`）。
- ⚠️ **数学字形画出根盒之外确实会让"并集"偏大**（实测 `\frac{a}{b}`：节点盒 28.7 高、并集 37.8 高）
  ⇒ **有节点的结构以节点盒为准**，并集只用来"兜住溢出"（点得到优先）。
- ★ **两条既有缺陷在这个过程里被抓出来**（都不在 ② 修，见《位点》§11.24 六）：
  `structureUnits` 的去重键不含位置（同层第二个同种结构被丢）；**「一原子多盒」**（`\sin` = 1 原子 3 盒）
  ⇒ 含多字母算子名的公式**点击定位失效**。

### 5.5 ★ 待拍板：包裹型结构的「结构层」怎么瞄（2026-10-15 晚，用户实测提出）

**事实**（探针数据见《位点与结构导航》**§11.17**）：

| 结构 | 装饰有没有"超出内容" | 结果 |
|---|---|---|
| **分式** | 分数线两头**超出**分子分母 | ★ "点分数线右端 = 整个分式"**天然有专属像素** ✓ |
| **根号** | 横线**不超出**被开方数 | ✗ 结构右缘 == 内容右缘 ⇒ **没有专属像素**；两个行为的分界只有 **1–2 px**（且"删整个根号"实际发生在公式**之外**，靠 §4.0 的"外侧委托内层"才得到同一结果） |

| 方案 | 做法 | 代价 |
|---|---|---|
| **(甲) 只加"看得见"** | 归属不变；做 §6.5「公式范围可见」（光标在公式里 → 整段淡范围） | 仍要瞄准内容右缘那几 px，但**里 / 外一眼可辨** |
| **(乙) 给包裹型一条"装饰带"** | 点在结构盒的**装饰高度带**（如最上 25%）= **结构层**（整个根号）；点在**字身带** = 内容层 | 装饰盒实测**完全失真**（1926×1078）⇒ 只能**启发式**推算；空槽结构要兜底 |
| **键盘（今天就有）** | 公式**外面**按 `←` → 结构层位点 → `⌫` 删整体；再 `←` → 内容末尾 → `⌫` 删内容 | 无（但要用户知道这条路） |

★ **建议顺序**：先 **(甲)**（纯加法、立刻可辨），(乙) 等 ② 落地后再评估。

★★ **2026-10-15 晚：已用第三条路解决 —— 「尾垫」**（见《位点与结构导航》**§11.18 / §11.18.1**）：

给 `\sqrt` 的内容末尾塞一段**看不见的 `\rule{3pt}{0pt}`** ⇒ 横线跟着变长 ⇒
**内容末尾与结构末尾分成两根像素**：点式子的右半边 = **内容末尾**（删 `2`）、
点横线那一截 = **结构末尾**（删整个根号）。

⇒ **不必**给包裹型做"装饰带"启发式（乙），也**不必**先等 ② 结构几何。
⇒ §四 的 ③④ 消费者里，**"根号末尾点不准"这一项划掉**；

## 六、维护约定（写给以后的我 / 下一个会话）

1. ★ **新增一个手感功能或修一个边界 bug 之前，先问："它消费哪张表？"**
   若发现要**自己再判一遍**（例如"这块是不是在公式里"）⇒ **停**，先把那张表补全。
2. ★ **不许在消费者里留第二份判据。** 今天 7 个 bug 里 6 个源于此（§三）。
3. ★ **凡"两个序列/坐标系必须对应"的映射，测试要全域断言**（完备 / 唯一 / 往返），不要逐例抽查。
4. ★ **为修复而写的测试，必须先证明它在修复前是红的**
   （做法：`git stash push -- app/lib` 收起源码改动、测试留着，跑一次）。
   本仓已因此抓出过三次"假通过"。
5. ★ **引擎行为一律实测，不读文档不猜**；实测结论落到代码旁的注释或守门人测试里
   （如 `multiline_math_test.dart` 头部那份 `\\` 数据表）。
6. ★★ **过闸表要用在**自己的**新功能上**（2026-10-15 晚的教训）：
   我照着 §6.5 做了"光标在公式里 → **整段淡色底**"，用户一眼看出来 ——
   **"给整段公式刷底色"正是 §7.2 过闸表里那条"公式有专用底色 = 症状"**。
   ⇒ **规格本身也可能带公式块味道**（§6.5 的动机是对的：里/外要看得见，W1 要能点），
   但**手段**要选"像文本装饰"的（两端刻度 / 细下划线），不要选"像卡片"的（整块底色）。
   ⇒ 新规矩：**任何给数学"加可见物"的改动，动手前先拿 §7.2 过一遍，并写进提交信息**。

7. ★★ **迭代节奏：一批讨论 → 一批实现 → 一次验证**（2026-10-16 用户定，全文见
   `全局笔记\开发守则.md` **§六**）：
   **探针期小步快跑；实施期成批改完再验证**（`analyze` ＋ 全量测试 ＋ 一次热重载验收）。
   别在实施期"改一点就跑一次全量" —— 每轮的固定成本会吃掉收益，还容易被本轮新暴露的 bug 拖长。
   一批的收尾固定为：**设计稿回写 → 快照更新 → 提交**。

## 七、★ 「同权」的精确边界与自检清单（2026-10-15 定）

> **第一位的那条原则**：**数学语言与文本地位等同** —— 文档里只有**一条**一串字符；
> 数学是这串字符**被渲染成的样子**，不是一个"对象 / 卡片 / 域"。`$` 是**渲染提示**，不是**语义墙**。

### 7.1 精确边界：`$` 不是层级，**嵌套结构是层级**

| | 是不是层级 | 后果 |
|---|---|---|
| `$` / `$$` / `{}` / `\text{}` 的**边界** | ★ **不是** | 它们**永远不是**编辑目标；"公式内 / 公式外"**不构成两个世界** |
| 结构嵌套（分子分母、被开方数、上下限、环境格） | ★ **是** | "点在结构外面还是里面"是**真问题** ⇒ 靠 ② 结构几何 |

⇒ **"公式块"的错不在于"有层级"，而在于把 `$` 当成一层。**
⇒ 一句话记住：**顶层无墙、内部有层。**

### 7.2 过闸表：出现任一症状，就是漂回"公式块"了

| 症状 | 为什么违反同权 |
|---|---|
| 有"**进入 / 退出公式**"这个概念（编辑态、模态、进出边界） | 文本没有"进入某个词"这回事 |
| 光标在公式**内 / 外**行为不同（除"纯语法事实"与"方向性语义"两类） | 那正是"两个世界"的定义 |
| **把 `$` 当成一层**：以公式为单位删除（旧 §4.0 的 B2/D2）、公式有专用快捷键 | 公式成了**胶囊** |
| 公式有**专用字号 / 专用底色 / 边框 / 卡片** | 数学被抬成"另一种东西" |
| 必须**先选中对象**才能改内容 | 文本里改字不需要先选中 |
| 内容被**自动搬进 / 搬出**公式（含"把 `/` 自动改写成 `\frac`"） | 违反"渲染是源码的忠实投影" |
| 因为"它在公式里"而换一套键位 | 同权 ⇒ 同一套键 |
| ★ **给公式画"范围"**（整段底色 / 外框 / 整段下划线 / 常驻高亮） | ★★ **它凭空造了一个数据里根本不存在的容器**：文档里只有一串字符，`$…$` 是**渲染提示**；对象 = **与光标同层的、紧邻的那一个渲染对象**（§4.0）—— `x_1+x_2=-\frac{b}{a}` 里是 **`x_1` · `+` · `x_2` · `=` · `-\frac{b}{a}` 五个彼此独立的对象**，**"多项式"不是对象、"公式"也不是对象**。范围高亮却把它们**画进同一个整体** ⇒ 等于造了个"公式对象"（用户 2026-10-16 的原话：`x_1+x_2=-\frac{b}{a}`、`x_1x_2=\frac{c}{a}` 这种式子里的**多项式结构竟被判定为一个整体**）。★ 允许的只有"**只在边界、且瞬时**"的刻度；见《位点》§6.5 的三条候选 |

★ **允许的区别只有两类**：
① **纯语法事实**（位点可达性、`^`/`_` 后面必须有组）；
② **方向性语义**（下一个字符进哪、`→`/`←` 的甲、`Tab`、`Enter` 守门人、选区、提交点）——
而**第二类必须靠"可见范围"让用户看得见**（§6.5），否则就成了"按了没反应"。

### 7.3 ★★ **块类型不是层级，也不是地位**（2026-10-16 定，用户提问逼出来的）

> 用户原话：「什么是**列表行**？**我们的行还有不同地位**？」

**背景**：Markdown 块类型（标题 `# ` / 段落 / 列表项 `- ` / 行间公式块 `$$…$$`）在**渲染**上确实不同
（字号、缩进、居中、标记），也确实是**四种不同的单元**。但实测发现一处**不该有的行为差别**
（《位点与结构导航》§11.25 第五轮）：**点右边的空白**在**列表项**上会夹到行末，
在**标题 / 普通段落**上却**落空** —— 原因只是列表项的内容被包在 `Row[标记, **Expanded**(内容)]` 里、
命中盒成了**满栏宽**（实现细节泄漏成了行为差异）。

| | 允许因块类型不同吗 |
|---|---|
| **渲染**（字号 / 缩进 / 居中 / 画不画标记） | ✅ **允许** —— 那是**排版意图**（源码里的 `# ` / `- ` 就是"我的排版意图"的记号） |
| **编辑行为**（点哪落哪 · 删什么 · `Tab` / `↑↓` · 选区 · 光标归属） | ❌ **一律不许** —— 否则就是"**同一段文字因为所处的块不同而地位不同**" |
| **源码里真实存在的标记字符**（`- ` 那两个字符） | ✅ 允许，但只能体现为"**纯语法事实**"（那两格本来就是字符、光标能落进去），不能变成"另一种编辑世界" |

⇒ **判据一句话**：把同一段文字分别放进 标题 / 段落 / 列表项，**同样的点击、同样的按键必须给同样的结果**。
⇒ **守卫测试**（随 ③-A 一起落）：同一段内容 × 三种块类型，在同一列空白处点击 ⇒ 落点必须相同（且 = 行末）。
⇒ 本条是 §7.1「`$` 不是层级」的推广：**`$` 不构成层级；块类型也不构成地位。**

### 7.4 ★★ 光标的"行"也按层级（2026-10-16 定，用户提出）

> 用户原话：「我们讨论的是**在数学语言后面的光标高度按照其内部子部位标准来画**的问题。
> 按道理来说**行内数学语言后面的光标跟文本后面的光标地位也是等同的**吧。」

**规则**（规格与实测见《位点与结构导航》**§11.27**）：

> ★★ 光标的"行"（高度 ＋ 竖直位置）按 **光标所在的那一层** 定，**不按"几何上最近的字形"**。
> · **文本流 / 公式之前 / 公式之后** ⇒ **文本层**标准（`当行字号 × 1.25`，贴文本基线）
> · **公式内部**（主行 / 分子 / 分母 / 上下限 / 次数 / 环境格）⇒ **那一层当地 ¶ 盒 × 0.84**

一句话：**"行内数学语言后面的光标"与"文字后面的光标"地位等同**（顶层无墙），
分子 / 分母 / 上下标各有各的行（内部有层）——
**判"行"先看层、再看层内最近**；不许拿"几何上最近的字形"跨层抢
（那正是"分式后面看着像分母的"根因：分母在公式末尾正下方、水平最近）。
