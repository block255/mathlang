## 三、✅ 风险 2 降级（2026-10-13 修订）：断点计算引擎已给，只剩"选行策略"

> **原结论只对了一半**：README 的 **❌ Breakable equations** 指的是 **Widget 不会自动替你折行**；但 **AST 层早已实现 TeX 规范的断点计算，而且是公开 API**。

**引擎已有能力**（2026-10-13 逐行核对 `flutter_math_fork 0.7.4` 源码）

| 能力 | 位置 / 签名 | 说明 |
|---|---|---|
| 断点计算（Widget 入口） | `Math.texBreak({relPenalty = 500, binOpPenalty = 700, enforceNoBreak = true})` → `BreakResult<Math>`（`lib/src/widgets/math.dart:241`） | 返回 `parts`（已切好的 `Math` 列表）+ `penalties`（各断点罚分） |
| 断点计算（AST 入口） | `SyntaxTree.texBreak(...)`（`lib/src/ast/tex_break.dart:12`） | 在 `bin`（二元运算符）与 `rel`（关系符）处切 |
| 官方建议用法 | 文档原文："assemble the pieces in whatever way you like. The most simple way is to put the parts inside a `Wrap`" | **`Wrap` 一包即可折行** |
| ★ 断行优先级 | 默认 **关系符 500（优先）< 加号/乘号 700**（TeX 惯例：罚分越小越优先断） | **正是本节原定 v2 的"关系符 > 加号 > 乘号"，引擎已内置** |
| 禁止断行 | 支持 `\nobreak` / `\penalty<n>`；默认 `enforceNoBreak: true` 时不暴露 10000 罚分点 | |
| 解析失败时的行为 | `ast == null` 或 `parseError != null` → 返回单段 + 罚分 10000 | **错误公式不会被切碎** |

**修订后的方案**

1. **v1**：`Math.texBreak()` 拿 `parts` → 按目标宽度**选行**（贪心即可）+ 续行缩进；简单场景 `Wrap` 兜底。`aligned` 按 `&` 对齐照旧。
2. **v1.5**：用 `penalties` 做动态规划选行（罚分总和最小），并加"不拆括号内部"等约束。
3. **v2**：续行缩进美化；跨页拆分与分页器联动（与 S2 合流）。

**仍然为真**：引擎**不会**自动折行 → **选行策略 + 续行缩进 + 与分页联动仍然是我们的活**；但**断点查找（最难的那半）不用自研**。

**验收**（不变）：一条 3 倍页宽的长公式能分成 3 行显示、语义不变、缩进美观。

### 4.0 ★ 目标架构：文字流内数学（用户 2026-10-13 提出并认可）

**要解决的问题**：主流产品（Word / MathType / Notion / Google Docs）把数学做成**内联对象** —— 进出有模式边界、删除是"整块删"、不能跨对象选中；Typora / Obsidian 走**源码**路线（编辑时露出 LaTeX）；**LyX** 是唯一把数学做成"文字流里的一等 inset"的成品。用户要的是**后者**：符号与结构**和普通字符同权**，能干脆地输入与删除。

**架构**

- **真相 = 一条一维字符缓冲区**（即存储的 md + LaTeX 源），**光标 = 一个整数偏移** → 插入 / 删除 / 选择 / 撤销 / 复制**全部复用文本编辑的成熟语义**。
- **渲染 = 投影**：缓冲区分段画 —— 文字段走 Flutter 文字排版，`$...$` 段交给 `Math.tex`，**同一行内基线对齐**；屏幕上不出现 `$`、不出现 `\frac`。
- **符号面板 / 快捷键 = "插字符 + 移光标"**：点「分式」→ 往缓冲区插入 `\frac{}{}`，并把光标偏移放进第一个大括号 → **"公式卡片"作为默认编辑方式不再需要**。
- **删除的粒度由映射决定**，不由"对象"决定：光标在普通字符处 = 删一个字符；光标紧贴已渲染结构边界 = **按结构删**（MathType / LyX 的 smart delete：先删内容、空了再删结构）→ **手感像删字符，又不会留下"半个坏公式"**。
- **点击定位**：用引擎的 `getCaretIndexForPoint` 反查源偏移；点分数线 / 根号横等"非字符元素" → 定义就近归属规则。

### 4.1 引擎已具备的"数学可编辑"原语（2026-10-13 核对源码 —— 本节最关键的新证据）

| 原语 | 位置 | 意义 |
|---|---|---|
| 每个 AST 节点带**源码偏移** `final int pos` | `lib/src/ast/syntax_tree.dart:133` | 渲染结果能**反查回源字符串第几个字符** |
| 每个节点带 `caretPositions`（该结构内**所有合法光标落点**） | `syntax_tree.dart:475` | 光标能落在哪儿由**引擎**算出，不靠猜 |
| `getCaretIndexForPoint(Offset)` / `getEndpointForCaretIndex(int)` | `lib/src/render/layout/line_editable.dart:361 / :386` | **像素 ↔ 光标位置 双向映射** |
| `node.pos + node.caretPositions[i]` | `lib/src/widgets/selection/selection_manager.dart:139` | 即"点屏幕 → 得到源偏移"的桥 |
| `CursorNode` + `\cursor` 命令（1.5px 光标竖条，**按公式基线对齐**） | `lib/src/ast/nodes/cursor_node.dart`、`lib/src/parser/tex/functions/custom/cursor.dart` | 引擎能在数学内部**画光标** |
| `findSelectedNodes(start, end)`、`TextSelection`、`sanitizeSelection` | `syntax_tree.dart`、`lib/src/widgets/controller.dart` | 数学内的**选区模型已有** |

→ **"AST 偏移 ↔ 像素"这条最难的桥，引擎已经给了。** 要自研的是**编辑策略**（提交规则、结构导航、混排），不是映射原语。

**仍需自研的三件难事（真正的工作量）**

1. **两套排版同行混排**：文字用 `RichText`/`TextSpan`、数学用 `Math` Widget，要同行基线对齐并一起参与断行；`WidgetSpan` 路线在长文档下的**性能需实测** → 实验问 0。
2. **跨边界结构导航**：从文字按 `→` 走进分子、再进分母；引擎给了 `caretPositions`，**但没给槽位间导航算法**，要自己写（MathType 的 `↑↓` 进槽位属这一项）。
3. **数学输入提交规则**：一维按键流 → 二维结构的挂载判定（例如 `x^2` 之后打 `+`，`+` 应在指数内还是主行内）。详见 5.1；本项目的对策是**"插入即明确 + 显式出槽"**，尽量不依赖启发式猜测。

### 5.1 数学输入提交规则（commit rules）—— A 路线的核心课题

一维按键流没有花括号来消歧，而用户又看不见花括号，于是**每次按键都要判定"挂到树的哪儿 + 光标何时离开当前结构"**。三种候选：

| 规则 | 行为 | 例子 | 风险 |
|---|---|---|---|
| 严格（显式出槽） | 只有 `Tab` / `→` 才离开槽位 | `x^2` 后打 `+` → 仍在指数内 | 最不会猜错，但按键更多 |
| 单原子 | 槽位里打完**一个**原子即自动出槽 | `x^2+1` ✅；`x^{2n}` ❌（得再进一次） | MathType Autoformat 的 `a^b` 属这个味道 |
| 上下文启发 | 在**槽位最外层**遇到关系符 / 二元运算符才出槽；显式分组（括号）内不出槽 | `x^2+1` ✅ 且 `x^{2n}` ✅ | 依赖"显式分组"当逃生门；边界情形必须实测 |

**我们的对策（兼得"不猜"与"顺手"）**：

1. **面板插入时连花括号一起写入缓冲区**（用户看不见）→ **机器永无歧义**，不需要猜。
2. 默认采用**上下文启发**做出槽，并**始终保留 `Tab` / `→` 显式出槽**。
3. 对**自动插入**的结构字符要有**回收（normalize）**机制，避免删着删着缓冲区积累空 `{}`；**normalize 只在提交点跑**（失焦、光标离开、粘贴完成），不在每次击键时跑。

#### 5.1.1 ★ 我们的解法：把"二维位点"**显式化**（用户 2026-10-13 提出，认可）

**关键认识**：二维结构里的光标位置**不是连续的二维坐标，而是离散、有限的一组"位点"**（分子槽 / 分母槽 / 指数槽 / 下标槽 / 矩阵的 m×n 个格…）。MathType、MathLive、LyX 全都是同一条路：**光标永远落在某个槽里**。

→ **于是"二维光标"是个伪问题**：把位点**按顺序枚举并编号**，光标就退化成一维索引 —— 而这**与一维缓冲区天然同构**（缓冲区偏移 ↔ 位点序**一一对应且顺序一致**）。**"数学与文字同权"和"结构内有二维位点"并不矛盾**，它们是同一个整数偏移的两种看法。

→ ~~**而且引擎已经替我们枚举好了**：`EquationRowNode.caretPositions` 就是"该节点内所有合法光标位置（相对偏移）的有序表"，配 `node.pos` 即得绝对偏移。**这就是位点表，不需要我们自己定义。**~~

> ⚠️ **2026-10-14 更正（此句已被 9.8 的实测推翻）**：`caretPositions` / `range` 是**渲染空间的编辑坐标**
> —— 只覆盖渲染出来的原子，**不含 `\frac{}` / `^` / `_` 等命令与结构字符**，
> 实测 `\frac{a}{b}=\sqrt{2}` 给出 `[2,3)[4,5)[6,7)[8,9)`，**根本不是源码下标**（见 9.8）。
> → **位点表与邻接表都必须我们自己在源空间建**，`visible_atoms.dart`（可见原子扫描器）是它的雏形。
> → 完整规格见 **《位点与结构导航.md》**（S3 的地基，用户 2026-10-14 确认按此推进）。

**读法（这三条直接决定 S2 怎么做）**

1. **成本几乎全在公式上**：100 行纯文字只要 142 ms，含公式 953 ms → 公式部分 ≈ 811 ms ÷ 100 ≈ **8 ms / 公式**。
2. **"一帧渲染整篇文档"不可行**（953 ms ≫ 16 ms 帧预算），**但"按页渲染"完全可行**：A4 一页约 25–30 行 → **≈300 ms 一次性**，可缓存，只在**翻页 / 编辑该页**时付出。
3. **旧的 2867 ms 是冷启动首帧**（含预热与断言）→ 复测为 953 ms：**首次布局远贵于稳态**，S2 需要为"首帧"设计预渲染 / 渐进渲染策略。
4. 推论：★ **打字时只能重绘"变化的那一个公式"**（解析 0.1 ms + 渲染 ≈8 ms），不能整页重排——这与 S1 清单里"只为变化的公式重绘"完全对上。

**④ 附带发现（A/B 实验）：`Math` 放进 `ListView` 列表项会触发布局断言** ★★

- **现象**：100 行含公式用 `ListView.builder` 渲染时出现
  `RenderBox was not laid out: RenderRepaintBoundary#… relayoutBoundary=up3 NEEDS-PAINT`（`box.dart:2251`），并伴随 `_debugDoingThisLayout`（`object.dart:2857`）与 `!semantics.parentDataDirty`（`object.dart:5724`）两条断言；界面表现为**列表刚渲染出前两行公式就换成异常面板**。
- **根因判定**：`ListView` 默认 `addRepaintBoundaries: true` → **给每个列表项包一层 `RepaintBoundary`**，该边界在布局完成前被读取尺寸（`Math` 的渲染子树内部含 `LayoutBuilder` 家族，`layout_builder_baseline.dart` 等）。
- **A/B 验证**：同一个 25 行公式列表，从 `ListView.builder` 换成 `SingleChildScrollView + Column`（**不产生 item 级 RepaintBoundary**）→ **三条断言全部消失** ✅（只剩实验页自身的 `RenderFlex overflowed`，属实验页布局问题）。
- ★★ **对产品的直接含义**：**文档视图、符号面板网格这类"滚动列表里放公式"的场景，必须避开默认的 item 级 RepaintBoundary**（`ListView(addRepaintBoundaries: false)`，或自建滚动容器）。**S2 / S4 必须实测这条**——否则"往上滚动看长文档"就会踩同一个坑。
- **可复现性**：两轮测量高度一致（176/306/953/142 ms → 173/334/998/130 ms），故结论可靠。

### 9.8 ③(b) 实现记录：零 src 依赖的"点屏幕 → 源偏移"（2026-10-13 23:00 · 已完成并验证）

**架构**（与 5.1.1「位点显式化」同构）

```
真实坐标点击
  ↓ 用 Math 的 GlobalKey 取渲染根盒 → globalToLocal 得局部坐标
渲染侧：遍历 Math 渲染子树收集"叶盒"（localToGlobal(ancestor: root) + size）
  ↓ 过滤掉两类"假叶盒"（见下表）
结构侧：★ 自己写的「可见原子扫描器」把 tex 词法化成 (可见原子, 源区间) 列表
  ↓ 两侧按**同一次序** zip（引擎保证 `GreenNode.children` 顺序 == 光标访问顺序）
取命中盒的左/右边界 → 源偏移 = 段起始 + 原子区间端点
```

**必须过滤掉的两类"假叶盒"**（本路线唯一的坑）

| 假叶盒 | 识别规则 | 为什么会有 |
|---|---|---|
| **根号分隔符**（装饰） | ★ **宽度上限**：盒宽 > `max(根盒宽 × 3, 32px)` 即为失真装饰盒（见下方 2026-10-14 修正） | 实测它的 `localToGlobal` 尺寸失真（x=26..1370, y=-2..1070），且它在 AST 里**不是**子节点（由父节点绘制） |
| **我们自己注入的 `\cursor{}` 光标条** | **宽度 ≥ 2px** | 光标条宽 1.5px；第一次点击后它就出现在渲染树里（`_BaselineDistanceBox`），会让叶盒数变成 5 vs 原子 4 |

> ⚠️ **2026-10-14 修正（S3-2 实测，本条推翻上面的旧判据）**：
> 旧判据写的是"真原子的矩形**必然落在 Math 控件边界内**"—— **这条不成立**。数学字形本来就会画出根盒之外：
>
> | tex | Math 根盒 | 字形盒 | 旧判据结果 |
> |---|---|---|---|
> | `x` | 16×**7** | y=-5..11（16 高） | 上边界 -5 < -4 → **误杀** |
> | `\frac{a}{b}=\sqrt{2}` | 74×29 | 分母盒 y17..33 | `Rect.contains` 的下边界是**开区间**（`bottom` 不含）→ **误杀** |
> | `\Delta = b^2-4ac` | 140×15 | 全部在内 | ✅ 侥幸通过 |
>
> → 旧判据下 6 个样本里**只有 1 个**"叶盒数 == 原子数"，而 `hitTestMathTex` 在数量不等时
> **静默返回 `null`** → **点屏幕定位对大多数公式悄悄失效**（界面表现就是"点公式没反应"，无任何报错）。
> → 新判据改为**宽度上限**：真原子与根盒同量级，而失真装饰盒大出几十倍（实测 1878px vs 根盒 74px）。
>   **6/6 样本全部通过**，回归测试见 `test/render/leaf_boxes_test.dart`。
>
> **另两处同批修正**：
> 1. `hitTestMathTex` 改为**两趟命中**：严格包含优先、落空才用"外扩/就近"。旧实现只做"外扩后第一个包含"，
>    会让**前一个盒把点抢走**（盒 2 = x41..57、盒 3 = x57..68，点 x=58 被盒 2 的外扩矩形 39..59 先匹配到 → 整整差一个原子）。
> 2. `lexVisibleAtoms` 对 `\sqrt[n]{body}` **按渲染顺序产原子**（KaTeX 的 sqrt 节点是 `[body, index]`，
>    源码顺序却是 `[index, body]`）并把 `[` `]` 当语法跳过。否则叶盒序与原子序整体错位，
>    点击次数会指到被开方数。

**★ 引擎的一个反直觉约定（必须避开，否则整条路线走不通）**

- `GreenNode.getRange(pos)` 返回 `TextRange(start: pos + 1, end: pos + capturedCursor)`，而 `capturedCursor = editingWidth - 1`
  → **单字符叶子的区间是 `[pos+1, pos)`（反的）**。
- 更关键：`range` / `caretPositions` 都是**渲染空间的编辑坐标** —— 只覆盖**渲染出来的原子**，**不含 `\frac{}`、`^`、`_` 等命令/结构字符**。
  实测 `\frac{a}{b}=\sqrt{2}` 给出 `[2,3) [4,5) [6,7) [8,9)`，**根本不是源码下标**。
- → **结论：源偏移必须由我们自己从 tex 词法化得到**（这就是「可见原子扫描器」存在的原因；它只跳过结构命令/`{}`/`^`/`_`/`&`/`\\`，其余每个字符或符号命令各算一个可见原子）。

**验证（三处抽查，全部命中预测值）**

| 点击位置 | 命中叶盒 | 可见原子 | 源偏移 | 实测缓冲区 |
|---|---|---|---|---|
| 分子 `a`（局部 6.1, 5.1） | #0 x=2..10 y=-1..13 | `a` [6,7) | 16+6 = 22 | **22** ✅ |
| 分母 `b`（局部 6.1, 20.7） | #1 x=4..15 y=15..29 | `b` [9,10) | 16+9 = 25 | **25** ✅ |
| `√2` 里的 `2`（局部 61.1, 10.9） | #3 x=56..66 y=-2..23 | `2` [18,19) | 16+19 = 35 | **35** ✅ |

**副产品（对后续阶段直接有用）**

3. 它同时给出了**原子边界** → 直接支撑"**按结构删除**（smart delete）"，也支撑行内公式的**选区**。

## 十、本轮新增的环境与 API 事实（2026-10-13，避免重复踩）

1. **`TexParser` 真实签名**：`TexParser(String content, TexParserSettings settings).parse()` → `EquationRowNode`（另 `settings.throwOnError` 默认 **true**，可当预校验用；实测 3 条公式解析均 **0.00–0.30 ms**）。

   > ✅ **2026-10-13 结果：(b) 已走通**（见 9.8），**无需 (a)/(c)**。
9. ★★ **Flutter Web（CanvasKit）自动化测试的一条铁律：语义树一开，CDP 坐标点击就失效。**

   **解决配方（让"读文本/坐标"与"精确点击"同时可用）**：
   ```js
   document.querySelector('flt-semantics-placeholder').click();  // ① 先启用语义树（用于读）
   const st = document.createElement('style');
   st.textContent = 'flt-semantics, flt-semantics-container, flt-semantics-host { pointer-events: none !important; }';
   document.head.appendChild(st);                                 // ② 再让语义层不拦指针
   ```
   此后 `browser_dock click {x,y}` 恢复真实坐标（实测局部坐标随点击位置正确变化），而 `flt-semantics` 仍可读（`textContent`/`aria-label` + `getBoundingClientRect`）。

10. **`GreenNode.getRange` 的区间约定**（9.8 详述）：单字符叶子返回 `[pos+1, pos)`（**反的**），且 `range`/`caretPositions` 是**渲染空间**坐标（不含命令字符）→ **不能当源下标用**，源偏移须自行词法化。

## 十一、S2-2 行内投影实测（2026-10-14 · `Text.rich` + `WidgetSpan`）

> 实验页：`app\lib\spike\s2_projection\s2_projection_page.dart`（实验台 →「S2-2 · 行内投影」）
> 被测：`app\lib\render\` 提炼后的 `InlineMathText`（`Text.rich` + `WidgetSpan(PlaceholderAlignment.baseline)`）
> 条件：A4 内容区宽 **657.6 px**（174 mm）、正文 16 px、行距 1.7

### 11.1 ★ 结论：折行 + 公式不被拆开，**免费得到**

| 样本 | 行数 | 段高 | 公式数 | 跨行的公式 |
|---|---|---|---|---|
| ① 长段落（3 个行内公式） | 2 | 56.0 px | 4 | **0** |
| ② 高结构（`\sum` 带上限 / 分式 / 根号 / 积分） | 2 | 56.0 px | 4 | **0** |
| ③ 超长单公式（宽 750 px） | 1 | 21.0 px | 1 | 0 |
| ④ 纯文字对照 | 2 | 54.0 px | 0 | — |

**判据**：18 个行内公式，**每一个的盒子都完整落在一个行盒内**（Δ上、Δ下 全部 ≥ 0）
→ **没有任何公式被拆到两行**。原因是结构性的：`WidgetSpan` 对行内排版器本来就是**原子盒子**。

→ ★ **S5「折行」的大半工作不用做**：换行直接交给 Flutter 的行内排版器。

### 11.2 高结构对行高的影响：**几乎可忽略**

含 `\sum_{i=1}^{n}` / `\int_{0}^{\infty}` 的段落行高 **27.7 px**，纯文字 **26.2 px** → **只高 1.5 px**。
（对 S2 分页的含义：按 26–28 px 估行高是安全的，不必为公式留大余量。）

### 11.3 `baseline` vs `middle`：**行数 / 段高 / 段宽完全相同**，只差 1–2 px 的竖向位移

| 公式 | baseline Δ上/Δ下 | middle Δ上/Δ下 |
|---|---|---|
| `$a_{i,j}+b^2$`（样本① #1） | 4.7 / 3.6 | 3.4 / 4.9 |
| `$\int_{0}^{\infty} e^{-t^2}\,dt$`（样本② #3） | 8.2 / 7.0 | 6.8 / 8.4 |

两者都是"盒子完整落在行盒内"，只是 `baseline` 让公式更**靠上**（贴合文字基线），`middle` 更**居中**。
**维持 S1 定稿：默认 `baseline`，保留 `middle` 回退。**

### 11.4 ④ 超长公式：**横向溢出**（S5 必须治）

宽 **750 px > 657.6 px**，引擎同时报 `A RenderLine overflowed by 110 pixels on the right.`
→ 与 S1「引擎不自动折行」一致。**S5 的活** = 用 `Math.texBreak()` 算断点 + 自己决定"在哪断、续行怎么缩进"。

### 11.5 本节新增的 API / 自动化事实（都是踩出来的）

1. ★ **`RenderParagraph` 没有 `computeLineMetrics()`** —— 那是 `TextPainter` 的能力，未公开。
   取「行盒」要用
   `getBoxesForSelection(TextSelection(0, len), boxHeightStyle: ui.BoxHeightStyle.includeLineSpacingMiddle)`
   再按 `top` 分组。
2. ★ **`getOffsetForCaret` 不能当"行号"用**：同一个行内它会**随字符 / 占位符抖动**
   （实测纯文字 3 行被数成 4 行；`getFullHeightForCaret` 也跟着给出 13.2 / 19.4 / 16.4 这种噪声）。
3. ★ **`WidgetSpan` 里的超长内容会让 `RenderLine` 在 paint 期抛溢出**；若错误钩子里**同步 `setState`**，
   会再抛 `Build scheduled during frame` → **帧管线被打断，该页之后所有点击静默失效**。
   修法：① 超长样本放进"足够宽的容器"；② 错误钩子只在**帧末**刷新（`addPostFrameCallback`）。
4. ★★ **`document.visibilityState == 'hidden'` 时 CDP 点击会静默失效** ——
   Chrome 的遮挡判定：窗口被别的窗口盖住 → 不产帧、不处理指针。现象与"点击没反应"一模一样，**极易误判成代码问题**。
   处置：**每次交互前先确认可见**；`window state=minimized` → 再 `normal` 可把窗口提回前台。
5. **要被自动化读回的报告不能用 `SelectableText`**（它的内容不进无障碍语义树）；用 `Text` 才能从语义树读出来。

### 12.1 ★ 结论一：`Offstage` 离屏测量**可信**

| 组 | N=25 冷布局 | 与真实渲染的高度差 |
|---|---|---|
| **A `Offstage` 离屏** | 114.6 ms | **0.000 px（25/25 全部取到）** |
| **C 真实渲染**（基准真值） | 117.7 ms | — |

`RenderOffstage.performLayout` 在 `offstage: true` 时**确实** `child.layout(constraints)`
（官方文档原话："can be used to measure the dimensions of a widget without bringing it on screen"），
只是不 paint / 不 hitTest、自身占 `constraints.smallest`（**不占地方**）。

**而且 A 与 C 的成本基本相同** → paint 在总成本里占比很小
→ ★ **分页不需要"先测量一趟、再渲染一趟"**，直接**"渲染即测量"**（需要提前知道高度时用 `Offstage`，代价一样）。

### 12.2 ★★ 结论二：真正的瓶颈不是布局方案，而是「每次 setState 重建整篇」

| 场景 | 缓存关 | 缓存开 | 提升 |
|---|---|---|---|
| 对照：什么都不改（N=25） | **91.1 ms** | **2.8 ms** | **32×** |
| 增量：只改 1 个单元（N=25） | 89.2 ms | **12.4 ms** | 7.2× |
| 对照：什么都不改（N=100） | — | **6.1 ms** | **O(1)**，与 N 基本无关 |

不开缓存时，**连"什么都不改"的空帧都要 91 ms** —— 整篇 25 个单元全部重建 + 重排。
这解释了浏览器实验里「A / C / 增量」三个数**几乎相等**（都被这个固定开销淹没），
也说明当时把注意力放在"选哪种测量方案"上是**找错了变量**。

**解法 = 单元级 widget 缓存**：源文本没变就复用**同一个 widget 实例**，
`Element.updateChild` 发现 `child.widget == newWidget` 会**整棵子树直接返回**（不 build、不 layout）。

### 12.3 附带发现（都很值钱）

1. ★★ **缓存必须按「位置」分桶，不能跨容器复用同一实例**：
   flutter_math_fork 的 `Math` 会把 `Line(key: GlobalKey)` 这个 widget **记忆化**
   （`syntax_tree.dart:547` 造 key，`:563` 挂到 `Line` 上）；同一个实例被放到树的两个位置 →
   `Multiple widgets used the same GlobalKey`。实测**只按 `i` 分桶立刻炸**（8 次异常），按 `tag/i` 分桶即干净。
   （顺带用探针排除了"同一公式出现两次"这个猜想——**那不会**冲突。）
2. ★ **build 比 layout 贵**：冷布局 114.6 ms（缓存关）→ 42.8 ms（缓存开），
   差的 72 ms **全是 widget 构造 + build 方法执行**的节省
   → **优化重点是减少 build，不只是减少 layout**。
3. **首次测量必须预热**：第一轮 A=185.5 / C=139.8 明显偏离，预热后收敛到 114.6 / 117.7
   （与 S1 的 release 基准教训同源）。
4. debug VM 下缓存开的最优打字帧 **12.4 ms**；release 通常再快 2–3.5× → 落在 60 Hz 预算（16.7 ms）内。
